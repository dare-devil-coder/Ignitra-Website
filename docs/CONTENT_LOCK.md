# Content lock and verification contract

site-content.json contains ordered, flat content records grouped by page and semantic section. It deliberately does not preserve legacy containers, classes, CSS, SVG geometry, components or code structure. Each record has an ID, authored text, computed display text, links/labels/alt data where applicable, and observed mobile/desktop theme visibility. The Stage 2 model may compose these records into new semantic components but must not change their copy.

legacy-snapshot.json is separately captured browser evidence, protected by lock.sha256. Its four repeat-visit, reduced-motion profiles cover mobile and desktop in dark and light. Reduced motion exposes all seven engine stages and final engagement status. Whitespace is collapsed; punctuation and computed text case are not normalized away. Visible links are compared with literal href and target; visible image alt text, section order, complete body text, title, language, meta and JSON-LD are compared too. Captured interaction state data is checked independently of the application JSON. There are no copy exceptions.

Stage 1 renders a deliberately plain content ledger at /. It is a real Next page reading the locked JSON, not a source-JSON self-comparison or a legacy iframe. It carries all static copy and assets required by the baseline. Menu/loop/form functionality and animated states are not implemented at this stage. Hidden records reflect source state/viewport visibility, not a workaround to hide a failing comparison.

Stage 2 must add behavioral tests that open the menu and dialog, select every loop state and consultation option, validate fields, and compare those rendered states with the existing independent state evidence. Add full text-node/attribute coverage for any newly observable server response once the old backend is supplied. Stage 3 must test animated completion, repeat visits and reduced motion; do not replace the reduced-motion baseline. Stage 4 must run both themes and all breakpoints, console and visual checks.

Public backend-generated errors cannot be extracted without the private implementation or exercising a live submission. They are an explicit evidence gap, not invented or silently exempted. The client success/pending/required-service messages are grounded in the public client bundle. The non-text theme toggle is the sole allowed new UI. Technical attribute differences are listed narrowly in allowed-diffs.json.

The first incomplete entrance-animation capture is archived unchanged in docs/initial-capture. Before any commit, a fresh source-only audit visited every heading and checked visibility. All authored text arrays were identical. The corrected baseline requires every main heading and all seven engine stages in each profile; verification fails early if that coverage is missing. Source accessibility/form attributes are also retained independently.
